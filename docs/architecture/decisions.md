## Storage / operations

- **2026-08-23 — [Warm-model residency + startup prewarm](decisions/2026-08-23-warm-model-residency-and-prewarm.md).** One process-wide `stage_cache` keyed `(stage, candidate_id)`, shared by `JobManager` and `StreamManager`, plus `prewarm_stage_cache()` on the FastAPI startup hook — every stage reports `build_s == 0.0` on the first job after boot (verified), where batch submissions previously rebuilt all 9 stages every time. `_free_accelerator_cache()` now runs only on a build. *Revisit:* memory pressure on a smaller box, or watch-along peak memory regressing from the skipped cache-free.

- **2026-08-01 — [Configurable storage roots + `library_root` publish](decisions/2026-08-01-configurable-storage-roots.md).** One `[storage]` table in `patmir.toml` owns every filesystem root (`runs_root`, `cache_root`, `downloads_root`, `state_root`, plus the new `library_root`); `patmir/paths.py` holds `StoragePaths` and `PipelineConfig.storage` carries it everywhere. Relative paths resolve against the config file's directory, replacing five divergent `Path.cwd() / "runs"` fallbacks. `library_root`, when set, gets each finished run's deliverables copied to `library_root/<job_id>/` (`out.mkv`, `out.hy.srt`, `dub.wav`) by a post-`output` runner step — copy not move, `.partial`-then-rename, never fails the run. Defaults reproduce the pre-change paths exactly. Storage is excluded from the cache key, so relocating the share never orphans a dub. Recommended layout: `runs_root` + `state_root` local, `library_root` (and optionally `cache_root`) on the network share — `runs/` is the live working dir with an appended-and-seek-tailed progress log, non-atomic per-stage manifest rewrites, and in-place ffmpeg writes. *Revisit:* per-section cache copies hurt watch-along latency over the network, a second machine needs to write the share (locking becomes load-bearing), or publishing needs a filename template instead of a per-job dir.

## Platform / hardware

- **2026-08-25 — [Cooperative job cancellation](decisions/2026-08-25-cooperative-job-cancellation.md).** Batch jobs had no cancel at all; watch-along's `stop` only halted the *scheduler*, letting the in-flight section run to completion, and a deliberate stop was recorded as `failed`. The accelerator lock made this urgent: a job can now sit in `waiting` behind a feature-length stream with no way to give up on it. **The constraint that decides the design: a Python thread cannot be killed.** Every stage runs via `asyncio.to_thread`, so `task.cancel()` abandons only the await while the thread keeps the GPU *and* the accelerator lock — a "cancelled" job would block the next one forever. So: a `threading.Event` per job (side dict, not on `JobRecord`, which is `asdict`-persisted) reaching `JobContext.cancel` — its own field, not `ctx.extra`, which is the *data* hand-off channel. Two cases: not-yet-started is instant and exact and never touches the accelerator; running is cooperative, `cancelling` → `cancelled` when the thread returns (which is also when the lock releases, so nothing starts early). Checkpoints at every stage boundary (bounded by tts, ~77 s) **and every TTS decode chunk (~8 s)** — the latter free, because the adapter raises from the `on_chunk` callback the candidate already invokes, needing no candidate change. Partial work is kept and the stage marked `cancelled` not `failed`, so `--resume-from` works. `POST /jobs/{job_id}/cancel` for both modes, idempotent; `/stream/<key>/stop` retained and now also trips the token. Found en route: `_process`'s `except Exception` would have swallowed `JobCancelled` and downgraded Stop to "one section failed". 14 tests; the load-bearing one asserts a second job runs after the first is cancelled and the lock is not leaked — exactly what a `task.cancel()` version would break while passing everything else. *Revisit:* Stop feeling slow (next lever is ASR's batched loop, not the decode inner loop); killing yt-dlp on cancel; or a resume-a-cancelled-job UI.
- **2026-08-25 — [One accelerator at a time](decisions/2026-08-25-one-accelerator-at-a-time.md).** A watch-along stream and a quality-mode dub submitted ~27 s apart both ran and exhausted the 3090 — three OOMs in 230 ms from two independent code paths, the last on a *tiny* `.to(device)` (once the card is full, allocation size stops mattering). **Not the WSL2 false-OOM:** commit was 51.84 GB limit / 43.34 used (8.5 GB headroom, pagefile already the corrected 20 GB) while the GPU sat at **24,105 of 24,576 MiB — 222 MiB free**. Cause: `create_app` shares one `stage_cache` between `JobManager` and `StreamManager` but they had **separate** locks, so each serialized its own work and nothing serialized them against each other. Resident weights are already ~15–16 GB (tts ~8.5, asr+aligner ~5.5, diarize 0.9, emotion, and *two* Demucs since batch takes `htdemucs_vocals` and watch-along `htdemucs_fast`) — one pipeline fits, two do not. The 2026-08-23 TTS unification had already found this constraint for the *weights* and it was never generalized to the *pipelines*. Fixed with one `asyncio.Lock` built in `create_app` and passed to both, held around each run body; a contended job reports a new `waiting` status (rendered in `popup.js`, whose fallback would have shown it as "Running… (0/0)"). **Deliberately coarse** — a batch job submitted mid-stream waits for the whole stream, which is the honest semantics when only one pipeline fits; the alternative is losing both. Known wart: the lock is held across the yt-dlp download inside `_run_blocking`. Guarded by 4 tests including a **negative control** asserting the bodies *do* overlap without the lock. *Revisit:* a second GPU or a bigger card; the download hold becoming annoying; or cancellation landing, which changes what a waiting job should do when the user gives up.
- **2026-08-24 — [TTS sampling: one RNG stream per sentence](decisions/2026-08-24-tts-sampling-reproducibility.md).** The author heard the final short word stressed on two lines (`…մեքենայի մեջ Ա`, `…արյուն ԿԱ`). Not quantization (bf16 native, no quantization on this path), not a sentence cut (both are complete), not the mux (the artifact is in the raw `tts/*.wav`), not an emotion tag. Measurable signature: unflagged lines end 6–19 dB **below** their own median chunk level, both flagged lines at or **above** it. Cause: `torch.manual_seed` was called once per *chunk* and the per-row sampler drew from that one stream, so a row's draw depended on its slot and its chunk-mates — and since chunks are formed by sorting **all** of a job's sentences by length, adding one sentence anywhere reshuffled every other line's prosody. Six runs of one clip put the same sentence's final level across a **26 dB** range. Fixed with a per-row `torch.Generator` seeded from a blake2b content hash of the request (plus the retry attempt, so retries still redraw); upstream's `_sample` takes no generator, so `_sample_codes` copies its 12 lines and the result is handed back to upstream's `_sampler_step` as a one-hot at temperature 0 so the delay/EOC state machine stays upstream's. **Buys reproducibility, not correctness:** same sentence set → byte-identical audio, call order irrelevant, identical rows in a chunk now match; but batching is still not bitwise-invariant *numerically* (batched matmuls + left-padded prefill at different shapes), which no seeding change can fix, so adding a sentence can still redraw unrelated lines. 38 % of short lines still end flat or rising. A punctuation hypothesis (62 % of translated lines are unpunctuated because Qwen3-ASR emits none) looked decisive at n=6 and died under a repeat control — identical input spreads 2.4–27.9 dB. **Methodological consequence: no TTS A/B here was measurable at n=1, including the same day's emotion-tag rounds (#15), which had one sample per cell.** Temperature measured and rejected as a lever (0.8/0.75/0.7/0.6 → 4/10, 2/10, 5/11, 4/12 flat endings, 0 overflows throughout). The lever that works is selection: best-of-2 → 21 %, best-of-3 → 4 %, at ~+22 s on a 139 s TTS stage — not implemented. *Revisit:* selection shipping (the metric then needs ear validation as a selector, and a target band beats a minimum — best-of-3 already selects at the extreme edge of the natural range); or a release that makes the batched decode bitwise-stable across shapes.
- **2026-08-24 — [One actor, one voice: duplicate speaker slots and per-word attribution](decisions/2026-08-24-speaker-identity-word-level-attribution.md).** An author ear-test listed nine timestamps where a character's voice changed mid-scene or spoke another character's line. Eight resolved to two mechanisms, and three separate symptoms shared one root cause: **Sortformer emitted one actor on two of its output slots** (SPEAKER_03 was 71 % concurrent with SPEAKER_02, seven turn pairs coinciding at 90–100 % of the shorter turn, five at total containment — against 8–10 % ragged overlap for the one genuinely distinct pair). That split the actor across two ref cells, disqualified 83 % of one slot's audio from ref-picking via *its own duplicate's* phantom overlaps (so it borrowed another character's clip — byte-identical audio for two characters), and put a spurious speaker change a few hundred ms into sentences. Second mechanism: `apply_speaker_tags` still left **another speaker's words in 13 of 76 sentences, 25 words of 393 in the wrong voice** — its 0.85 dominance gate let small intruders through (idx 20 measured 0.811) and its single boundary came from a *turn start*, which on concurrent turns lands at the sentence start and leaves a one-word half the non-lexical guard discards. Fixes: `merge_duplicate_speakers` in the shared Sortformer post-processing (aggregate containment ≥ 0.6 over ≥ 1.0 s, union-find, most-speech id survives, relabelled turns re-merged because `derive_overlaps` assumes one speaker never overlaps itself), and **per-word speaker attribution** replacing dominance-plus-one-boundary — words labelled by max turn overlap, grouped into runs, one sentence per run, with a wobble rule (≤ 2 words, same speaker both sides → absorb; the measured interior overlap is an exact tie, so only the A-B-A shape can decide it) and an edge rule (short terminal run absorbed only if the neighbour fits it at least as well as its own label — which is what lets `"Зачем"` survive as a one-word line). On the clip: 4 speaker ids → 3, SPEAKER_02's longest eligible ref window 2.92 s → 4.52 s, no borrowed voices, 76 → 88 sentences. 31 new tests. **Not fixed:** the 4-speaker cap, now the largest remaining identity problem (at least six characters speak; the squad roll-call runs entirely on two ids while the other two sit idle), and the per-utterance timbre drift the author heard at 0:17.5, which is Higgs re-cloning off a short ref — same id, same emotion, same file. *Revisit:* a clip where two people genuinely cross 0.6 aggregate containment; an ear-test finding one-word fragments worse than the mis-voiced words they replaced; or diarization gaining more than four identities, which would change what these heuristics are compensating for.
- **2026-08-24 — [ASR sentence segmentation, and what the first CUDA baseline actually measured](decisions/2026-08-24-asr-sentence-segmentation-and-cuda-baseline.md).** Both Qwen3 ASR candidates emitted one `Sentence` per ASR chunk and never called `group_into_sentences`, so from the 2026-07-14 flip onward "sentence" meant "up to 28 s of audio" on **both machines** — 23 sentences against diarization's 108 turns on a 5-minute clip, spans to 26.3 s, and because `apply_speaker_tags` assigns one *dominant* speaker per sentence, **several characters were dubbed in one voice**. `performance.md` had filed the symptom as a TTS-tail performance follow-up for a month; it was a quality bug. Fixed in both candidates (+ a `_boundary_time` bug that never split when the dominant speaker was the later one, + a `max_sentence_s` cap for gapless runs): 23 → 81 sentences, max span 26.3 → 6.96 s. Also: `patmir bench --mode batch` was not measuring the warm path it claimed to (no `stage_cache`; 45 % of wall on torch), `transformers` floor raised to `>=5.13` in the shared extra, and `[emotion_guidance]` **deleted** after being found inert since the Higgs swap. First CUDA baselines: batch warm **0.461** (M1 Pro 1.17), watch-along **1.42** aggregate but **0.831 steady-state — the first time watch-along has cleared realtime on any machine**. Environment finding: CUDA under WSL2 charges Windows *commit* ~1:1 per GB of VRAM, so the pagefile — not the 24 GB card — set the allocation ceiling. *Revisit:* an ear-test finds the 8 s sentence cap cutting mid-utterance; a clip puts 3+ speakers in one grouped sentence (`apply_speaker_tags` splits only once); or Qwen3-ASR gains punctuation output.
- **2026-08-23 — [CUDA port slice 1: machine profiles + the torch candidate set](decisions/2026-08-23-cuda-port-machine-profiles.md).** Dev machine moved to a WSL2 + RTX 3090 box, where four of the five model stages could not run (MLX-only). `[pipeline.profiles.<name>]` overlays the stage selectors so ONE committed `patmir.toml` serves both machines — selected by `PATMIR_PROFILE` (or `--profile`, which exports it), resolving `[pipeline] < profile < code overrides < profile.<layer>`; the `<layer>` tier exists so a profile can displace `streaming_config()`'s hardcoded MLX overrides. Autodetection from `torch.cuda.is_available()` was rejected (a benchmark must be attributable to a stated choice) and an unknown profile name is a hard error. The `cuda` profile selects `htdemucs_vocals` (new: `vocals_only` ported to the torch candidate), `qwen3_asr_1_7b` (rewritten against transformers' **native** `qwen3_asr`, added in 5.13.0 — the official `qwen-asr` package pins `transformers==4.57.6` exactly, mutually exclusive with the Higgs checkpoint's `>=5.5`, and installing it broke a working TTS stage. 5.13 satisfies both, so ASR stays the same model family on both machines and the dep set shrinks; the `-hf` checkpoints are required, and long-form segmentation moved into the candidate as VAD-snapped batched chunks. `faster_whisper_large_v3_fp16` was the interim pick and stays the no-Qwen fallback), `sortformer_nemo` (new: the SAME Sortformer model on NVIDIA's own NeMo, sharing post-processing with the MLX candidate — so diarization stays at parity instead of falling back to pyannote), `higgs_v3_torch_bf16` (new: same Higgs model, reusing the checkpoint's own sampler/delay helpers but owning the decode loop so it runs **batched across sentences** — upstream's `generate_speech` is batch-1, the wrong shape for a bandwidth-bound decode, and TTS is ~69% of batch wall; batch-vs-single equivalence verified bitwise on a tiny CPU model. Flash-attention turned out NOT to be available upstream, contrary to the plan). Mechanism verified on the Mac (284 tests, distinct cache keys per profile, no MLX module selected under the profile in either mode); **nothing CUDA has been executed yet.** *Revisit:* upstream flags flash-attention or batched decode; or the measured 3090 baseline lands far from the ~0.35 batch / ~0.51 watch-along projection.

## Phase 3 (near-realtime watch-along)

- **2026-08-25 — [Watch-along startup latency and stall causes](decisions/2026-08-25-watchalong-startup-and-stall-causes.md).** Author reported a slow first chunk and periodic freezes on a 1297 s YouTube video (WSL2 + 3090) and asked for benchmarking — which was itself the first finding: the **live stream recorded no timing at all** (`sections.json` held `{index, start, end, file}`), and `bench --mode watch-along` bypassed `StreamManager`/`StreamScheduler` entirely and took a local file only, so the reported video could not be benchmarked as submitted. The session was reconstructed from artifacts still on disk (measurements preserved in the spec folder): **72.4 s to first audio** for a 40 s window, steady-state RTF ~0.87 with 0.4 s idle between sections (serial, no lookahead), and the prelude computed **three times**. Causes fixed: **(A1)** `_snap_window_end` took `max(end <= target)` over VAD intervals, but Silero's `speech_pad_ms=500` makes runs separated by under ~1 s of silence come back **touching**, so an end equal to the next start is *mid-speech* — one section cut at 8.1 s after analyzing 38 s (RTF 4.0), discarding 8 of 10 sentences; now a candidate needs a real gap AND must not fall below half the target. **(A3)** a pause over 45 s killed the stream permanently, because abandonment keyed off *playhead* movement and the client stops POSTing while paused, and `submit()` then returned the `done` record; abandonment now keys off the client still polling, and an incomplete `done` stream restarts. **(C1)** a restarted stream re-seeded coverage but restarted its section index at 0, overwriting `section_001.wav` while `append_section` deduped by *start* and kept both entries — **wrong audio at 154.9 s and 190.3 s, live and on every rewatch**; the shape is now unrepresentable and an already-damaged manifest self-heals. **(B1)** a chunk costs `max(steps)` and greedy splitting left 9 sentences as `[8, 1]` — the trailing chunk one line, **17.3 s of a 41.6 s stage**; balanced chunking gives `[5, 4]` at the same memory ceiling and is identical when `max_batch` divides evenly. **(B2/B3)** the 14.3 s gap between ASR and translate that no stage owned was the two non-stage models loading lazily inside the prelude — measured 18.0 s, of which the age/gender profiler is **15.2 s** and ECAPA only 2.9 s — plus the streaming candidate set never being prewarmed at all; both now prewarm at boot. **(B4)** ASR re-probed the language every section (3.5-4.6 s) though the prelude knew it. Telemetry: one shared reader for bench and production, per-section timing persisted additively (incl. `other_s` = wall minus stage sum, ~1.6 s/section and previously invisible), and bench gains `--url`, a scheduler-driven mode with a synthetic viewer that **counts stalls**, and `time_to_first_audio_s`. 75 new tests, each pinned to a measured failure. **Not measured end to end on the 3090 yet**, and buffer policy (pre-buffer, section pipelining, unbounded ECAPA list growth) is deliberately deferred until it is. *Revisit:* the snap's 0.5 target fraction cutting a good boundary; an ear-test on the mid-utterance fallback cut; or watch-along gaining a second worker, which makes the whole-stream accelerator lock binding.
